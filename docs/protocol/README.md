# VishasBody 데이터 프로토콜 (Body → Vishamos)

Body(웹캠 바디 트래커, 시그니처 31)가 Vishamos(시그니처 11)로 보내는 바이너리의 형식이다. Vishamos 쪽 수신 구현용.

- 기준: 기술 명세 [`docs/tech_spec/01_body_packet.md`](../tech_spec/01_body_packet.md). 이 문서는 받는 쪽이 지킬 부분만 옮긴 것이다. 둘이 다르면 명세가 맞고, 이 문서를 고친다.
- 접속·등록·헤더 `[to, from]`·에러 규칙은 VishaSynapse 프로토콜(`Vishamos/VishaSynapse`의 `docs/protocol/README.md`)을 따른다. 이 문서는 그 뒤의 데이터만 다룬다.
- 상태: **확정** (2026-11-22). 트래커 구현 완료, 구현 현황은 명세에 적는다.

---

## 1. 요약

| 항목 | 값 |
|---|---|
| 경로 | Body(31) → VishaSynapse → Vishamos(11), WebSocket 바이너리 메시지 |
| 빈도 | 카메라 프레임마다 1개, 초당 약 30회 |
| 크기 | **1,080바이트 고정** (검출 여부와 관계없이 항상 같음) |
| 숫자 | 리틀 엔디언. 실수는 float32 |
| 좌표계 | **Unity 좌표계로 변환된 값** (§4) |
| 메시지 종류 번호 | **31** |
| 버전 | **1** |

## 2. 바이트 배치

| 오프셋 | 크기 | 형식 | 이름 | 내용 |
|---|---|---|---|---|
| 0 | 1 | u8 | `to` | 11 (Vishamos). VishaSynapse 헤더 |
| 1 | 1 | u8 | `from` | 31 (Body). VishaSynapse 헤더 |
| 2 | 1 | u8 | `kind` | 31 = Body 프레임 |
| 3 | 1 | u8 | `version` | 1 |
| 4 | 1 | u8 | `flags` | bit0 몸 검출, bit1 왼손 검출, bit2 오른손 검출. 나머지 비트는 0 |
| 5 | 3 | u8 × 3 | `reserved` | 0. 정렬용 예약 자리. 받는 쪽은 무시한다 |
| 8 | 4 | u32 | `seq` | 시퀀스 번호. 트래커 시작 후 1부터 프레임마다 1씩 증가(보내지 못하고 버린 프레임은 건너뜀) |
| 12 | 4 | u32 | `timestamp_ms` | 이 프레임을 카메라에서 읽은 시각. 트래커 시작 후 경과 ms |
| 16 | 528 | f32 × 132 | `pose` | 몸 33점 × (x, y, z, visibility) (§3.1) |
| 544 | 268 | f32 × 67 | `left_hand` | 왼손 21점 × (x, y, z) + 손바닥 회전 (qx, qy, qz, qw) (§3.2) |
| 812 | 268 | f32 × 67 | `right_hand` | 오른손, 형식은 왼손과 같음 |
| **합계** | **1,080** | | | |

- 왼쪽/오른쪽은 **사람 기준**이다(화면 기준 아님). 트래커 화면의 거울 모드는 데이터에 영향이 없다.
- 해당 flags 비트가 0인 부위는 값이 모두 0이다. 값으로 검출 여부를 추측하지 말고 flags를 본다.
- `seq`·`timestamp_ms`와 모든 float가 4바이트 경계에 정렬되어 있다. 오프셋 16부터는 float 268개가 빈틈없이 이어진다. C# 예:
  ```csharp
  ReadOnlySpan<float> f = MemoryMarshal.Cast<byte, float>(data.AsSpan(16, 1064)); // 복사 없음
  // 몸 i번 점: f[i*4 + 0..3] = x, y, z, visibility
  // 왼손 j번 점: f[132 + j*3 + 0..2], 왼손 회전: f[195..198]
  // 오른손 j번 점: f[199 + j*3 + 0..2], 오른손 회전: f[262..265]
  uint seq = BinaryPrimitives.ReadUInt32LittleEndian(data.AsSpan(8));
  ```

## 3. 데이터 의미

### 3.1 몸 (`pose`)
- MediaPipe Pose의 33점, 번호 순서 그대로. 주요 번호: 0 코, 11·12 어깨, 13·14 팔꿈치, 15·16 손목, 23·24 골반. **홀수 = 왼쪽**(사람 기준).
- 위치: 미터, **원점 = 양쪽 골반의 중심**.
- `visibility`: 0∼1, 그 점이 화면에 보일 가능성. 앉은 방송 자세에서 골반은 책상에 가려 0에 가깝다(값은 모델이 추측한 것). 골반은 고정하거나 약하게만 반영하고, 몸통 방향은 어깨선 위주로 계산하길 권한다.

### 3.2 손 (`left_hand`, `right_hand`)
- MediaPipe Hand의 21점, 번호 순서 그대로: 0 손목, 1∼4 엄지, 5∼8 검지, 9∼12 중지, 13∼16 약지, 17∼20 소지(각 손가락은 뿌리 → 끝).
- 위치: 미터, **원점 = 그 손의 손목(0번)**. 0번은 항상 `(0, 0, 0)`이다. 몸에 붙일 때는 몸 §3.1의 손목(15·16) 위치에 손 좌표를 그대로 더한다.
- 손바닥 회전 `(qx, qy, qz, qw)`: Unity `new Quaternion(qx, qy, qz, qw)` 순서. 다음 손 좌표축을 나타낸다.
  - +z(forward) = 손목 → 중지 뿌리(9번) 방향 (손가락이 뻗는 쪽)
  - +y(up) = 손바닥이 향하는 쪽 (손바닥 면에 수직)
  - +x = Unity 왼손 좌표계 기준 나머지 축
  - 즉 `Quaternion.LookRotation(손가락 방향, 손바닥 방향)`과 같다.
- 손이 검출됐어도 손바닥 방향을 계산할 수 없는 프레임(점이 한곳에 겹침)에서는 회전이 `(0, 0, 0, 0)`이다. **네 값이 모두 0이면 회전 없음**으로 보고 이전 회전을 유지한다.
- 위치만으로는 아래팔 비틀림과 손 뒤집기를 알 수 없으므로 이 회전을 쓴다.

## 4. 좌표계

트래커가 MediaPipe 좌표를 **Unity 좌표로 변환해서** 보낸다. 받는 쪽은 변환 없이 쓴다.

| 축 | 값 (Unity) | 사람 기준 |
|---|---|---|
| +x | Unity 오른쪽 | 캐릭터의 오른쪽 |
| +y | 위 | 위 |
| +z | 앞 | 캐릭터가 바라보는 쪽 |

- 기준: 캐릭터가 Unity +z를 바라보고 서 있을 때, 사람이 오른팔을 들면 캐릭터도 오른팔(+x 쪽)을 든다.
- 캐릭터를 거울처럼(사람 왼팔 = 캐릭터 오른팔) 움직이려면 받는 쪽에서 x 부호를 바꾸고 **왼쪽/오른쪽 번호도 서로 바꾼다**(좌표만 바꾸면 팔이 엇갈린다).
- 체형이 사람과 다르므로, 절대 위치보다 점 사이 **방향**으로 뼈 회전을 계산하길 권한다.

## 5. 받는 쪽 처리 규칙

- **수신 버퍼는 1,080바이트 이상**이어야 한다. (현재 Vishamos 1KB → 확장 필요)
- 앞 3바이트로 거른다: `from == 31`이고 `kind == 31`일 때만 이 형식으로 읽는다. `version`이 다르면 버리고 로그를 남긴다. 길이가 1,080이 아니면 버린다.
- **순서**: WebSocket(TCP)이라 보낸 순서대로 도착한다. 순서를 맞추려고 `seq`로 버릴 필요는 없다.
  - `seq`가 1보다 크게 건너뛰면 트래커가 그 사이 프레임을 보내지 않은 것이다(정상 동작, 지연 방지를 위해 밀린 프레임을 버림).
  - `seq`가 이전보다 작아지면 **트래커가 다시 시작된 것**이다. 스무딩·속도 계산 상태를 초기화한다.
- `timestamp_ms`의 차이를 스무딩의 dt로 쓴다(수신 시각보다 정확하다). `seq`가 작아지면 함께 다시 시작한다.
- 트래킹을 놓쳤을 때(flags 비트 0): 마지막 자세 유지 또는 기본 자세 복귀. 어느 쪽인지, 몇 초 뒤에 복귀할지는 Vishamos가 정한다.
- 트래커 연결이 끊기면 메시지가 오지 않는다(VishaSynapse는 알려 주지 않음). 일정 시간(예: 1초) 수신이 없으면 놓친 것과 같게 처리한다.

## 6. 변경 이력 관리

- 바이트 배치나 의미가 바뀌면 `version`을 올리고 이 문서와 명세를 함께 고친다.
- 새 종류의 메시지를 만들면 종류 번호를 32, 33…으로 잡고 이 문서에 절을 추가한다.
