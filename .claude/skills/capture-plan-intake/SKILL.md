# 기획서 반영 절차

## 원칙
- 기획서 원본은 노션 `VishaSTD / VishasBody`와 하위 페이지. 다른 프로그램 페이지는 보지 않는다. 단, Body와 맞물리는 `VishaSTD / VishaSynapse`의 `[Synapse-…]` 항목(시그니처, 메시지)은 비교용으로 읽는다.
- **사람이 작성·점검하고 Claude는 읽기만 한다.** (노션 쓰기 도구는 deny)
- 기획서대로 무조건 만들지 않는다. 구현 전에 확인하고, **답을 받기 전에는 추측으로 채우지 않는다.**
- 기획서 수정이 필요해 보이면 직접 고치지 않고 "기획 검토 요청"으로 알린다.

## 1. 읽기
- 노션 검색·조회 도구로 해당 페이지를 읽고, 마지막 수정 시각을 기록해 둔다.
- 비교 대상: 현재 코드, README, `docs/tech_spec/`, worklist, VishaSynapse `docs/protocol/README.md`.

## 2. 검토 (항목마다)
| 관점 | 예 |
|---|---|
| 실현 가능성 | MediaPipe 제약(GPU 없음, 앉은 자세 골반 가시성 0), 30 FPS 예산 |
| 누락 | 데이터 형식, 좌표계·단위, 검출 실패 시 동작, 빈도·크기 |
| 충돌 | VishaSynapse 규약, 기존 결정(README "결정과 이유"), 현재 코드 |
| 위험 | 방송 화면 노출, 프레임 저하, 연결 끊김 |

## 3. 보고 (사용자에게)
- 일치 / 불일치(노션↔코드, 노션↔명세, 노션↔Synapse 규약) / 결정 필요 질문으로 나눠 보고한다.
- 근거를 단다: 기획 태그(`[Body-<영역>-<이름>]`. 기획 항목에 붙이며 작업 단위가 아니다. 이름은 중복·변경·재사용하지 않는다), 코드는 파일:줄.
- 태그가 없거나 형식이 어긋나거나 중복이면 함께 알린다.

## 4. 기술 명세로 옮기기 (합의 후)
- `docs/tech_spec/NN_<주제>.md`에 작성한다. 상단에 상태(`초안`/`승인`), 근거 노션 페이지와 수정 시각, "항목 구분" 정의를 적는다.
- 표의 `근거` 열에는 기획 태그만 적는다. 노션에 없는 사용자 결정은 "사용자 답변"으로 적고 `docs/work/plan_review.md`에서 노션 이전을 관리한다.
- 명세 끝에 "구현 현황" 표(항목, 상태, 커밋)를 둔다.

## 5. 작업으로 나누기
- worklist 항목 형식: `- [ ] <번호> <내용> — 기획: [태그] / 명세: <문서 번호> §<절>`
- 진행을 막는 질문은 plan_review에, 막지 않는 것은 worklist "결정 대기"에 둔다.
