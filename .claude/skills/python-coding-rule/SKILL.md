# Python 코딩 표준과 수정 절차

## 0. 기준
- 구현 기준은 기술 명세(`docs/tech_spec/`) 하나다. 노션은 메인 세션이 명세로 정리한다.
- 서버 규약(시그니처, 등록, 메시지 헤더, 에러·종료 코드)은 VishaSynapse `docs/protocol/README.md`에서 읽는다. 스킬·기억·README 요약에 의존하지 않는다.
- 이 스킬과 어긋나는 작업(예: 기존 파일을 통째로 다시 쓰기)이 필요하면 하기 전에 "규칙 예외 제안"으로 알린다.

## 1. 분석
- worklist에서 맡은 항목과 근거(기획 태그, 명세 절)를 확인하고 그 명세 절을 읽는다.
- 대상 파일을 끝까지 읽고 Grep으로 사용처(`import`, 호출부)를 찾아 영향 범위를 확인한다.

## 2. 런타임과 의존성
- Python 3.12 기준(mediapipe 지원 버전). 표준 라이브러리를 우선한다(`struct`, `threading`, `queue`, `unittest`).
- 새 의존성 추가는 사용자 승인이 필요하다. 추가하면 README "환경"에 버전과 함께 적는다.

## 3. 프레임 루프
- 메인 루프(카메라 → 추론 → 그리기)에서 블로킹 I/O를 하지 않는다. 네트워크 송신은 별도 스레드에서 하고, 메인 루프는 최신 프레임 데이터만 넘긴다(크기 1 큐 또는 최신값 덮어쓰기). 밀린 프레임은 보내지 않고 버린다(실시간 데이터).
- 프레임마다 도는 새 작업은 비용(ms)을 추정해 보고에 적는다. `stats.py`의 단계별 시간에 넣을 수 있으면 넣는다.
- 스레드 간 공유 상태는 `threading.Lock` 또는 `queue.Queue`로만 주고받는다. (C#의 `lock` / `ConcurrentQueue`에 해당)
- 종료 시 스레드를 정리한다: 종료 이벤트(`threading.Event`) 설정 → 소켓 닫기 → `join(timeout)`.

## 4. 바이너리 패킹
- `struct` 형식 문자열은 항상 `<`(리틀 엔디언, 패딩 없음)로 시작한다. 형식 문자열과 크기(`struct.calcsize`)는 모듈 상수로 한 번만 정의한다.
- 프로토콜 값(시그니처, 메시지 종류 번호, 버전, flags 비트)은 상수로 정의해 쓰고 숫자를 직접 적지 않는다.
- 패킷은 고정 크기다. 검출되지 않은 부위는 flags 비트로 표시하고 값은 0으로 채운다.
- 바이트 배치 자체는 이 스킬에 적지 않는다. 기준은 기술 명세다.

## 5. WebSocket 송신
- 접속 직후 등록을 보내고 `client.registered`를 받은 뒤에만 바이너리를 보낸다. 등록 전 데이터는 버린다.
- 끊기면(예외·close) 일정 간격으로 다시 접속하고 다시 등록한다. 재접속 대기 중에도 트래킹은 계속 돈다.
- 서버 ping에 pong이 자동 응답되는지, 쓰는 라이브러리 기준으로 확인해 보고에 적는다.
- 서버 주소는 코드에 하드코딩하지 않는다. git에서 제외한 설정 파일 또는 명령줄 인자로 받는다.
- 에러는 예외 종류와 종료 코드만 로그에 남긴다. 받은 메시지를 프레임마다 출력하지 않는다.

## 6. 스타일
- 기존 파일의 들여쓰기, 명명 방식(snake_case 함수, PascalCase 클래스), 줄바꿈(CRLF)을 유지한다. Edit로 수정한다.
- 주석은 한국어로, "왜 그렇게 했는지"가 코드만으로 드러나지 않을 때만 단다.
- 내 변경으로 안 쓰이게 된 `import`·변수·함수는 지운다. 원래 있던 죽은 코드는 내가 고치는 함수 안에서만 지우고, 그 밖은 보고만 한다. `pose_test.py`는 비교용 보관본이라 고치지 않는다.

## 7. 자체 확인 (에러가 없는지만 본다)
1. **문법 검사** (바뀐 파일마다, `py_compile` 금지):
   ```bash
   python -c "import ast,sys; [ast.parse(open(f, encoding='utf-8').read(), f) for f in sys.argv[1:]]" <파일들>
   ```
2. **단위 테스트**: `python -B -m unittest discover -s test`
3. **스모크 테스트** (웹캠 없이 `main.main()` 실행):
   - 스크립트는 `.temp/`(git 제외)에 Write 도구로 만들고 `python -B .temp/<파일>.py` 한 줄로 실행한다.
   - `cv2.VideoCapture`, `cv2.imshow`, `cv2.waitKey`, `cv2.namedWindow`, `cv2.setMouseCallback`, `cv2.getWindowProperty`를 가짜로 바꾼다. `getWindowProperty`는 1을 돌려줘야 한다(아니면 창이 닫힌 것으로 보고 루프가 끝남).
   - 서버가 필요하면 테스트 안에서 `127.0.0.1`의 기본이 아닌 포트에 가짜 서버를 띄운다. 실제 VishaSynapse 서버에 접속하지 않는다.
   - 끝나면 스크립트를 지운다.

## 8. 테스트 작성 (`test/`, 커밋 대상)
- 위치: `test/test_<모듈>.py`, 프레임워크: `unittest`.
- **기대값은 명세에서 가져온다.** 구현 코드는 호출 방법(함수 이름, 인자)을 알 때만 본다. 작성자와 같은 해석 오류를 피하려는 것이다.
- 어느 PC에서 받아도 그대로 돌아야 한다: 웹캠·실제 서버·절대 경로·새 의존성 없이, 전체 실행은 수 초 이내.
- 바이너리는 경계값을 포함한다: 검출 없음(flags 0), 한쪽 손만, 패킷 크기, 헤더 바이트 값.

## 9. 보고 형식
1. **처리 항목**: 항목 번호, 기획 태그, 구현한 명세 절. 항목마다 완료 / 질문으로 멈춤 / 규칙 예외 제안. 구현하며 세운 가정.
2. **흐름 대응표**: `함수(파일:줄) → 명세 § → 확인 방법과 결과`. 사용자는 C#에 익숙하므로 낯선 Python 개념은 C# 대응을 짧게 붙인다.
3. **변경 파일**: 파일:줄, 한 줄 요지.
4. **자체 확인**: 문법·단위 테스트·스모크 테스트 각각 통과/실패, 실행하지 못한 것과 이유. "확인한 항목"과 "사용자가 확인할 항목"(실제 웹캠·서버 연동)을 나눈다.
5. **프레임 예산**: 프레임마다 추가된 작업의 추정 비용.
6. **범위 밖 발견**: 손대지 않은 문제와 어디를 고쳐야 하는지(받는 쪽 앱, VishaSynapse 포함).
7. **사용자 질문**과 **이슈 후보**(상황, 구현해 둔 임시 동작, 다른 선택지)를 나눠 적는다.
8. **문서 반영 내용**: 명세 "구현 현황"에 넣을 줄, README에 반영할 결정·측정값.
